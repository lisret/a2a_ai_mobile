## Task quality: Changes requested

The implementation is functionally correct for every path exercised by the required tests and faithfully reproduces the intended contract shapes. However, comparing against sibling Wave-2B adapters (OpenClaw, Codex, Cursor) that consume the same frozen `VisualAgentUpstreamPort`/`VisualAgentProtocolCodec` seam surfaces real robustness gaps introduced by this task that those siblings specifically guard against.

### Important

1. **Unguarded synchronous throws inside the upstream message listener.** `handleUpstream(message)` in both `DshAdapter.ts` and `HermesAdapter.ts` calls `decodeVisualAgentMessage(message)` directly, and `forward(event)` calls `this.tracker.accept(event)` directly — both of which `throw new CapabilityError(...)` on any malformed frame, sequence regression, or task/session correlation mismatch. This call happens inside the callback passed to `session.subscribe(...)`, with no `try`/`catch` anywhere in the call chain. A single malformed or mis-correlated frame from the upstream bridge will throw synchronously out of an event-listener callback whose caller (the real, non-test `VisualAgentUpstreamSession` implementation) is not guaranteed to catch it — this can crash the notification pipeline instead of gracefully failing.
   Sibling adapters avoid exactly this: Codex/Cursor's `handleUpstream` uses a **non-throwing** `normalizeUpstreamMessage` that returns `null` on bad input; OpenClaw's `handleUpstreamMessage` uses inline duck-typing that returns early rather than throwing. Both patterns exist precisely so a bad frame is silently ignored (or should transition connection state to `failed`/`visual_agent_protocol_error`) rather than throw inside a listener. Task 11's adapters never produce a `visual_agent_protocol_error` failure state at all, despite that literal existing in `VisualAgentErrorCode` for exactly this case.
   Not caught by any test: the fixtures only ever emit well-formed, correctly-correlated frames via `encodeVisualAgentMessage`, so this path is never exercised.
   *Suggested fix:* wrap the body of `handleUpstream` in a `try { ... } catch { this.state = {status:'failed', errorCode:'visual_agent_protocol_error'}; /* optionally close session */ }`, mirroring the fail-closed pattern used everywhere else in these same files.

2. **`DshBindingV1.declaredCapabilities` is validated but never consulted for capability gating.** The brief's own type signature requires this field on the DSH binding, and `DshBinding.ts`'s normalizer conservatively defaults it to all-false and only lifts explicit `true` flags — matching the "no CLI-text inference" intent. But `DshAdapter.ts`'s `connect()`/`execute()` never reads `binding.declaredCapabilities`; all gating is done purely against whatever `session.negotiate()` (the injected, test-controlled upstream) returns. In production this means the DSH binding's own declared ceiling is forwarded as opaque payload to the upstream port but is not locally enforced as an independent constraint — if a buggy or compromised upstream implementation ever negotiated a capability the binding explicitly declared unsupported (e.g. `approval`), this adapter would trust it. The implementer's report states "`declaredCapabilities` defaults to all-false and only explicit `true` flags are honored," which is accurate only for the binding validator, not for the adapter's actual negotiation/gating path — the report's design notes slightly overstate what is enforced at the adapter layer.
   This does not fail any brief-mandated test (none test this exact scenario), and is arguably consistent with treating the injected upstream as the sole authority (as siblings without a binding-level `declaredCapabilities` field do), but it does leave an explicitly-modeled safety field functionally inert.

### Minor

3. **`requestPreferences()` always resolves `undefined`, discarding the actual upstream response.** Both adapters fire `preference.request` and immediately `return undefined` without correlating the eventual `preference.result` frame (which is decoded by `handleUpstream` but simply dropped in the `default:` branch of the switch). OpenClaw's sibling implementation does full request/response correlation via a pending-request map; Codex's sibling returns a stub `{type:'list', preferences:[]}`. Task 11's behavior is the least complete of the three but is consistent with the brief (which does not test this path) and with the frozen conformance runner (which never inspects `requestPreferences()`'s return value). Worth reconciling before any UI wiring depends on real preference data.
4. **`DshExecutionPort`/`HermesExecutionPort` are near-verbatim duplicates** (identical except manifest, binding validator, tool id, and request-id prefix). The implementer flagged this themselves as an intentional trade-off to stay inside the owned-directory boundary; reasonable given the ownership constraint, but a candidate for later consolidation.
5. **`closeSession()` is not best-effort.** Unlike OpenClaw's `closeSessionQuietly` (try/catch, "disconnect is best-effort"), both adapters' `closeSession()` calls `await session.close()` unguarded. If `close()` throws while tearing down after a capability-unsupported failure in `connect()`, that exception would replace/mask the intended `CapabilityError('visual_agent_capability_unsupported')` being thrown right after.
6. **No dedicated test for the "unknown/blank version fails closed" branch** in `DshExecutionPort.connect()` (`binding.version.trim().length === 0`). The logic exists and is plausible, but only the two brief-mandated tests plus the conformance suite were written, so this specific fail-closed path is unexercised by the test suite.

### Critical

None found. No hard constraint from the brief or global-constraints list is violated; the gaps above are robustness/completeness issues in code paths the required tests do not exercise, not violations of the stated contract, privacy, or default-disabled/fail-closed rules.
